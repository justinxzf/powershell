# PowerShell AI Session Summary

将当前 Claude Code 会话内容总结并保存为结构化 Markdown 文档。

## 执行步骤

1. **定位 transcript 文件**：从当前会话的 `transcript_path` 或环境变量 `CLAUDE_TRANSCRIPT_PATH` 获取 JSONL 对话记录路径

2. **读取并解析对话记录**：
   - 使用 Read 工具读取 transcript JSONL 文件
   - 如果文件较大（超过 2000 行），分批读取，优先提取 `type` 为 `human` 和 `assistant` 的关键消息
   - 解析每行 JSON，提取 `type` 为 `human` 和 `assistant` 的消息
   - 提取每条消息的文本内容、工具调用记录和文件变更

3. **话题识别与拆分**：
   - 通读全部对话内容，按话题（而非时间轮次）进行分组
   - 话题识别标准：用户提出了新的问题、新的需求、或切换了讨论主题，即视为新话题
   - 同一话题内的多轮交互归入同一章节，即使中间穿插了简短的偏题讨论

4. **话题拆分预确认**：
   - 列出识别到的话题列表（编号 + 简短标题），例如：
     1. 实现 NL 检测优化
     2. 修复终端显示 bug
     3. 新增配置项支持
   - 使用 AskUserQuestion 向用户提出两个问题（multiSelect）：
     - **问题一「选择要包含的话题」**：列出所有话题作为选项（multiSelect=true），用户勾选需要记录的话题，未勾选的话题将被排除。默认全部选中
     - **问题二「需要合并的话题」**：列出所有话题作为选项（multiSelect=true），用户勾选希望合并的话题。选中多个话题将合并为一个章节。不选则保持各自独立
   - 如果用户选择了合并，将选中的话题合并为一个章节，章节标题取第一个话题的标题，内容按时间顺序组织
   - 排除和合并处理完成后，继续生成

5. **补充文件变更信息**：
   - 执行 `git diff --name-status` 获取变更文件列表及操作类型（A=新增 / M=修改 / D=删除）
   - 执行 `git diff --stat` 获取变更统计（增删行数）
   - 如果当前项目不在 git 仓库中，跳过此步骤，仅依赖 transcript 中的变更记录
   - 将 git diff 结果与 transcript 中解析到的变更合并，**以 git diff 为准**，transcript 中的变更描述作为补充说明

6. **确认输出目录**：
   - 检查 skill 调用时的 `args` 参数
   - 如果 args 非空（如 `/powershell-ai-summary ~/Desktop`），将其作为输出目录，跳过询问
   - 如果 args 为空，使用 AskUserQuestion 询问用户：
     - 提供两个选项：「当前目录」和「桌面」，用户也可在"Other"中输入自定义路径
     - 默认使用当前工作目录（`.`）

7. **按话题生成结构化 Markdown**：
   - **标题**：整体会话标题，概括本次会话涉及的核心领域
   - **日期**：当前日期时间
   - **摘要**：1-3 句话概括本次会话的核心目标和成果
   - **话题章节**：每个话题独立一个二级标题章节，章节内包含：
     - **话题描述**：用户提出的问题或讨论的话题（1-2 句话）
     - **最终方案**：该话题最终采纳的技术方案，**必须详细**，包括：
       - 方案的核心思路和设计决策
       - 关键代码变更的说明（涉及哪些文件、改了什么、为什么这样改）
       - 配置项或参数的具体取值
       - 如有代码片段，保留最终版本的完整代码
       - 关键变更附上 `文件路径:行号` 引用，便于定位源码
     - **输出文档**：如果 AI 在该话题中输出/创建了 Markdown 文档，列出文档的完整路径
     - **未采纳方案**：如果讨论过程中有过其他方案但最终未采用，在章节末尾列出：
       - 方案简述（1-2 句话即可，不需要详细）
       - 不采用的原因
   - **文件变更汇总**：以 git diff 结果为准列出所有变更文件，标注操作类型和变更说明；无 git 仓库时使用 transcript 解析结果
   - **关键命令**：列出执行的重要 shell 命令

8. **保存文件**：
   - 文件名格式：`PowerShell_会话_{核心话题关键词}_YYYYMMDD.md`
   - 核心话题关键词从会话标题中提取（取前 2-4 个汉字/单词）
   - 多话题时使用第一个话题的关键词，或使用"多话题"概括
   - 如果同一天已存在同名文件，追加时分：`PowerShell_会话_{关键词}_YYYYMMDD_HHmm.md`
   - 完整路径：`{输出目录}/PowerShell_会话_{关键词}_YYYYMMDD.md`
   - 使用 Write 工具写入

9. **告知用户**：用中文回复，包含文件路径和一段简短摘要

## 输出格式示例

```markdown
# 会话标题

**日期**：2026-04-22
**摘要**：本次会话主要完成了 X 功能的开发和 Y 问题的修复。

---

## 话题一：实现 X 功能

**话题描述**：用户希望实现 XXX 功能，用于解决 YYY 问题。

### 最终方案

（详细描述最终采纳的技术方案，包括设计思路、关键代码变更、配置说明等）

关键变更：
- `Sources/xxx.swift:42` — 重构了 NL 检测逻辑
- `Services/NLDetector.swift:15` — 新增规则匹配分支

**输出文档**：
- `/path/to/output/doc.md`

### 未采纳方案

1. **方案 A**：使用 ZZZ 方式实现。不采用原因：性能不满足要求。
2. **方案 B**：通过 WWW 途径解决。不采用原因：与现有架构不兼容。

---

## 话题二：修复 Y 问题

**话题描述**：用户反馈 YYY 场景下出现 ZZZ 错误。

### 最终方案

（详细描述最终方案）

### 未采纳方案

1. **方案 C**：修改 AAA 模块。不采用原因：影响范围过大。

---

## 文件变更汇总

| 文件 | 操作 | 变更统计 | 说明 |
|------|------|----------|------|
| `Sources/xxx.swift` | M | +32 -8 | 添加了 X 功能的实现 |
| `Services/yyy.swift` | A | +45 -0 | 新增 YYY 服务模块 |
| `Tests/test_zzz.swift` | D | -120 | 移除废弃测试 |

## 关键命令

- `swift build` — 编译项目
- `swift test` — 运行测试
```

## 注意事项

- **按话题组织，而非按对话轮次流水记录**：不要逐轮记录"用户说了什么、AI 回复了什么"，而是提炼每个话题的最终成果
- **最终方案务必详细**：这是文档的核心价值，读者应能根据此部分还原完整的技术决策和实现细节
- **未采纳方案适度简略**：只需让读者知道"还考虑过什么、为什么没用"，不需要展开
- **如果 transcript 文件不可读**，直接基于当前对话上下文生成总结
- **单话题会话**：如果整个会话只围绕一个话题，仍然使用相同的章节结构，只是只有一个话题章节
- **文件变更以 git diff 为准**：transcript 可能遗漏部分变更，git diff 更精确；变更汇总中增加变更统计列
